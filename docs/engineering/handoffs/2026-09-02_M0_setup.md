## 4. Eiichi向けセットアップ手順（この順で1つずつ）

1. ブランチを取り込む: `git fetch origin && git checkout claude/m0-setup-implementation-evj203`（PMがmainへのマージを判断）
2. `cd apps/web && npm install`
3. `.env.local` が `apps/web/.env.local` にあることを確認（`.env.example` と同じ4変数）
4. `cd ../..`（リポジトリ直下）で `npx supabase login` → ブラウザで承認
5. `npx supabase link --project-ref <ref>`（`<ref>` は Project URL `https://<ref>.supabase.co` の部分。DBパスワードを聞かれたらプロジェクト作成時のもの）
6. `npx supabase db push` → 3本のマイグレーションが適用される
7. Supabaseダッシュボード → Authentication:
   - Sign In / Providers → Email → **Confirm email: ON**
   - URL Configuration → Site URL `http://localhost:3000`、Redirect URLs に `http://localhost:3000/**`
   - （推奨）Email Templates を token_hash 形式に変更（`apps/web/README.md` §2-2）
8. `cd apps/web && npm run dev` → `http://localhost:3000/signup` で登録 → 確認メールのリンク → `/` に「レシピはまだありません」
9. 検証: `npm run lint && npm run test && npx playwright install chromium && npm run e2e`
10. 型を再生成してコミット: リポジトリ直下で `npm run db:types` → `apps/web/lib/supabase/database.types.ts` の差分を確認して commit
11. Vercel: `apps/web/README.md` §4 の手順（Root Directory = `apps/web`、環境変数4つ）。デプロイURLを Supabase の Site URL / Redirect URLs に追加

## 6. 設計上の判断（指示書の範囲内で決めたこと）

- `created_by` は `profiles(id)` を参照し、既定値 `auth.uid()`
- 子テーブル（材料/手順/タグ/買い物アイテム）のRLSは親経由の security definer ヘルパーで判定（ポリシー再帰と性能のため）
- `meal_plans` の with check は「自グループ かつ 自グループのレシピ」
- サインアップ時の表示名は `signUp` の `options.data.display_name` → メールのローカル部 → 「ユーザー」の順。個人グループ名は「{表示名}のグループ」
- `/update-password` はリカバリーセッション必須のため保護対象（未ログインは `/login` へ）
- パスワード再設定メールは登録有無を漏らさないよう常に成功表示
- Storage の `recipe-images` は 10MB / jpeg・png・webp・heic・heif に制限

## 7. PM確認事項

1. **全テーブルに `updated_at` を付与**: 指示書のスキーマ表では `group_members` / `recipe_ingredients` / `recipe_steps` / `recipe_tags` / `meal_plans` / `shopping_items` に `updated_at` がないが、CLAUDE.md「全テーブルに created_at, updated_at」に従い全テーブルへ付与した。問題なければそのまま
2. **groups / group_members の書き込みポリシーは未作成**: グループ作成はサインアップトリガーのみ。招待・脱退・グループ名変更以外の書き込みは M4（共有）で追加する想定。`groups` は select/update のみ、`group_members` は select のみ許可
3. **profiles は本人のみ閲覧可**: M4 でパートナーの表示名を出す際にポリシー拡張が必要
4. **パスワード最低文字数をアプリ側で8文字**にした（Supabase既定は6）。ダッシュボード側も8に揃えるか要判断
5. **メールテンプレートの変更を推奨**: 既定の `ConfirmationURL` はPKCE前提で「登録したのと同じブラウザ」でしか確認リンクが機能しない（スマホのメールアプリ等で別ブラウザが開くと失敗）。README §2-2 の token_hash 形式に変更すれば別ブラウザでも動く。Eiichi作業に含めてよいか
6. **`database.types.ts` は手書き**: `supabase gen types` はリンク済みプロジェクトが必要なため、マイグレーションから同形式で起こした。手順10で再生成して置き換える前提
7. **E2E と `db reset` はこの環境で未実行**（§3）。Eiichi実行を待つか、PMがローカルSupabase（Docker）を前提にした検証方針を立てるか
8. **`/settings/profile` を追加**: 受け入れ条件1（表示名の同期）の確認に必要なため指示書外だが最小限で追加した
9. **Storage の容量/MIME制限**（10MB・画像のみ）は指示書にないEngineer判断。M1の画像アップロード仕様に合わせて変更可
10. `supabase/config.toml` の `major_version = 17`（CLI既定）。ホスト側のPostgresが15の場合、`db reset` 用ローカルのみの設定なので実害はないが、揃えるなら要変更

# MaiRecipe 仕様（唯一の真実）

このファイルが仕様の正。Issue・ADR・実装がここと食い違ったら、PM が指摘して Eiichi に確認する。
1機能ごとの詳細設計は `docs/superpowers/specs/` に置き、ここからリンクする。

## 1. 一言で言うと

見つけたレシピを取り込み、自分好みに改良して、献立と買い物までつなげる Web アプリ（PWA）。

## 2. 誰のために・何を解決するか

毎日献立を考えて買い物をする人。まずは Eiichi と一緒に使う人。
レシピがブックマーク・動画・SNS にバラバラで、作ってみて気づいた「こうすればよかった」も残らない。
「何を作るか」から「何を買うか」までが毎回ゼロからになる問題を解決する。
基本の流れは **探して取り込む → 改良する → 献立に入れる → 買い物する**（DEC-010）。
将来はレシピを投稿・アレンジし合える SNS を目指す（今は作らない）。

## 4. やらないこと（Out of scope）

- メール + パスワードでの本番ログイン（DEC-009）。ネイティブアプリ（まずは Web / PWA）
- AI が裏で勝手に動くこと（DEC-012）
- 取り込み元の文章・写真のコピー（DEC-011）
- 今は作らないが、後で相談するもの：
  - お料理アシスタント（料理モード：手順の読み上げ・声で「次」・動画のその場面へ。料理中の AI への質問）。見た目を詰め直してから
  - レシピ SNS（公開・人気レシピ・フォロー・アレンジ）。データに author_id と visibility だけ先に持っている

## 5. 技術スタックと制約

- Cloudflare Workers **無料プラン**1つ。画面（React + Vite の PWA）と API（Hono、`/api/*`）を同じ Worker で配る（DEC-008）
- DB は D1（SQLite）+ Drizzle。写真も当面 D1（1枚 1MB 以下）
- ログインは Better Auth の Google ログイン（DEC-009）
- 1回の処理の CPU は 10ms まで。画像の縮小は端末、取り込みは HTMLRewriter の流し読みだけ
- 日本語 UI。スマホ縦（375px）基準、PC でも崩れない
- 詳細は `CLAUDE.md`

## 6. データの考え方（主要エンティティと関係）

- **グループ**が所有の単位。ユーザーは必ず1つ以上のグループに属し、個人利用時は1人グループ（DEC-004）
- D1 には RLS が無いので、グループの判定はセッションからだけ行い、DB へのアクセスは `src/api/data/` の `forGroup` だけを通す
- 例外は1つだけ：グループをまたぐ「自分宛ての招待を読む・参加する」は `src/api/data/membership.ts` に閉じ込める。宛先は確認済みのメール（emailVerified）だけで決める
- **レシピ**（recipes）は見出し（最新版の名前・カテゴリ・ジャンル・出典・動画・author_id・visibility）
- **版**（recipe_versions）が材料・手順・名前を丸ごと持つ。seq は通し番号で、消しても詰めない。種類は 元のレシピ / メモから更新 / 自分で編集
- **メモ**（recipe_memos）はどの版に反映したかを持つ（版を消すと未反映に戻る）
- **献立**（meal_plans）は「日付 × 朝昼晩 × 並び順（position）つきの複数レシピ」。1枠に複数品、同じレシピは1枠に1回まで。参加でぶつかった枠は両方残し、招待した側の品が先
- **買い物の印**（shopping_marks）は「材料名|単位」ごとに「家にある」「買った」を持つ
- 写真は recipe_images（D1 の BLOB）。公開時に R2 へ移す

## 7. 品質基準

- テスト: `src/shared/`・`src/api/`・マイグレーション・バグ修正は必須。画面の見た目は例外
- グループをまたいだ漏れ（他の人のデータが 見える・変えられる・消せる・献立に入る）がないことを、API テストで毎回確かめる
- レビュー: `reviewer` エージェントの Critical が 0 になるまでマージしない
- PR 前に `npm run lint && npm run typecheck && npm run test` が通ること

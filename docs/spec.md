# MaiRecipe 仕様（唯一の真実）

このファイルが仕様の正。Issue・ADR・実装がここと食い違ったら、PM が指摘して Eiichi に確認する。
1機能ごとの詳細設計は `docs/superpowers/specs/` に置き、ここからリンクする。

## 1. 一言で言うと

Web・SNS・料理本・自作のレシピを1つのフォーマットで保存し、献立づくりから買い物リストまで回せる Web アプリ。

## 2. 誰のために・何を解決するか

毎日献立を考えて買い物をする人。レシピがブラウザのブックマーク・SNSの保存・紙の本にバラバラに散らばっていて、
「何を作るか」から「何を買うか」までが毎回ゼロからになる問題を解決する。
レピッタ（repitta.com）の機能構成をそのまま踏襲する。差別化は狙わない（Eiichi の学習・制作が目的）。

## 4. やらないこと（Out of scope）

- OAuth ログイン（Google 等）。メール + パスワードのみ
- ネイティブアプリ。Web のみ
- レピッタにない差別化機能
- MVP 時点での課金（機能フラグで後付けする）

## 5. 技術スタックと制約

- Next.js 15（App Router）+ TypeScript strict / Tailwind v4 / shadcn/ui
- Supabase（Auth / Postgres / Storage / Edge Functions）、Vercel にデプロイ
- AI は Anthropic SDK。呼び出しはサーバー側のみ。クライアントに API キーを置かない
- DB アクセスは必ず RLS 前提。`service_role` key はサーバー / Edge Function 内のみ
- 日本語 UI。レスポンシブ必須（スマホ縦・PC）
- 詳細は `CLAUDE.md`

## 6. データの考え方（主要エンティティと関係）

- **グループ**が所有の単位。ユーザーは必ず1つ以上のグループに属し、個人利用時は1人グループ
- ユーザー所有物は `owner_id` ではなく `group_id` で持つ（将来の共有対応のため）
- **レシピ** に 材料 / 手順 / タグ がぶら下がる
- **献立** は「日付 × 食事区分（朝昼晩）× レシピ」の紐付け
- **買い物リスト** は献立・レシピの材料から生成され、買い物アイテムを持つ
- レシピ画像は Storage の `recipe-images` バケット（private、パスは グループ/レシピ 単位）

## 7. 品質基準

- テスト: ロジック・データ層は必須、画面の見た目は例外（eiichi-rules §6）
- レビュー: `reviewer` エージェントの Critical が 0 になるまでマージしない
- PR 前に `npm run lint && npm run typecheck && npm run test` が通ること
- RLS は「他ユーザーのデータが1件も見えない」ことを E2E で検証する

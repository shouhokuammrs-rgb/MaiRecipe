# パートナーの招待（#14）設計

- 日付: 2026-09-29
- Issue: #14（M5 共有と課金）
- 決めたこと（Eiichi, 2026-09-29）: 参加時は相手のデータを共有グループへ移す / 招待は Google のメールアドレスを入力 / 自分以外4人まで / 献立の枠がぶつかったら招待した側を残し、参加完了の画面で知らせる / 抜ける機能は今回作らない

## 1. 目的と完了条件

レシピ・献立・買い物リスト（印を含む）を、招待した人と同じものとして使えるようにする。

完了条件
- 招待前: お互いのデータが見えない。招待されていない人は参加できない
- 参加後: 両方から同じレシピ・献立・買い物リストが見え、どちらからも編集できる
- 参加した人の元のレシピ・献立・印・報告は共有グループに移っている
- 献立がぶつかった枠は、参加完了の画面に「10月3日の夜は、もとの献立を残しました」のように出る
- `npm run lint && npm run typecheck && npm run test` と E2E（2人で招待→参加→同じレシピが見える）が通る

作らないもの: 抜ける・メンバーを外す、メール送信、グループ名の変更、プラン判定（M5 の課金まで上限は常に「自分以外4人」）

## 2. ユーザーの流れ

招待する人（A）
1. 設定画面「いっしょに使う人」で、相手の Google のメールアドレスを入れて「招待する」
2. 一覧に「招待中：b@example.com」と出る。「取り消す → 本当に取り消す？」の2回押しで取り消せる
3. 相手にアプリを開くよう、自分で伝える（メールは送らない）

招待された人（B）
1. そのメールアドレスの Google アカウントでログインすると、レシピ一覧の上と設定画面に「A さんから招待が届いています」と出る
2. 「参加する → 本当に参加する？（あなたのレシピ・献立は A さんのグループに移ります）」の2回押し
3. 参加完了の画面: 「参加しました」＋ 移したレシピの数 ＋ ぶつかって残さなかった献立の枠の一覧（あれば）
4. 以後は A と同じデータが見える

設定画面「いっしょに使う人」には、メンバーの名前（本人には「（あなた）」）と招待中のメールアドレスを出す。
ローディング／エラー／空状態をそろえる。

## 3. データ

新しいテーブル `group_invites`

| 列 | 型 | 説明 |
|---|---|---|
| id | text PK | |
| group_id | text → groups（cascade） | 招待したグループ |
| email | text | 小文字にそろえた相手のアドレス |
| invited_by | text → user（set null） | 招待した人 |
| created_at | integer | |

- unique(group_id, email)。参加したら行を消す。取り消しも行を消す
- 上限: メンバー数 + 招待中の数 ≤ 5（自分以外4人）

既存テーブルの変更は無い（`group_members.role` の owner / member をそのまま使う。招待した人の側は owner、参加した人は member）。

## 4. API

グループの判定はこれまで通りセッションからだけ。クライアントから group_id は受け取らない。

| メソッド | パス | 誰が | 内容 |
|---|---|---|---|
| GET | /api/group | メンバー | グループ名・メンバー（名前・自分かどうか）・招待中のメールアドレス |
| POST | /api/group/invites | メンバー | { email } を招待。自分・既にメンバー・上限超えは 400/409 |
| DELETE | /api/group/invites/:id | メンバー | 自分のグループの招待を取り消す。他グループの id は 404 |
| GET | /api/invites | ログイン中の人 | 自分のメールアドレス宛ての招待（招待した人の名前・グループ名） |
| POST | /api/invites/:id/accept | 宛先の本人 | 参加する。返り値は { movedRecipes, keptPlans: [{date, meal}] } |

- 宛先の判定は、セッションのユーザーのメールアドレス（Google で確認済み）と招待の email が一致するかだけで行う。一致しなければ 404（招待があるかどうかも教えない）
- 参加できるのは、今のグループに自分しかいないときだけ（自分が誰かを招待済みでメンバーがいる人は参加できない: 409）。招待中の行があれば一緒に消す

## 5. データ層（forGroup の例外を1つだけ作る）

参加はグループをまたぐ操作なので、`forGroup` の外に `src/api/data/membership.ts` を1つ作り、ここだけに閉じ込める。

- `invitesFor(email)`: 自分宛ての招待だけを読む
- `acceptInvite(inviteId, user)`: 次を D1 の batch（1つのトランザクション）で行う
  1. 招待が本人宛てか・上限内か・自分のグループが1人だけかを確かめる
  2. ぶつかる献立の枠（同じ日付・朝昼晩）を読み、参加する側の行を消す（keptPlans として返す）
  3. ぶつかる買い物の印（同じキー・種類）と報告（同じ URL）も参加する側を消す（招待した側を残す）
  4. recipes / recipe_versions / recipe_memos / recipe_images / meal_plans / shopping_marks / import_reports の group_id を、自分の1人グループから招待したグループへ書き換える
  5. group_members の自分の行を招待したグループ（member）に付け替え、空になった1人グループと招待の行を消す
- グループのメンバー・招待の一覧と招待の追加・取り消しは、これまで通り `forGroup` に足す

CPU 10ms の制約: 書き換えは UPDATE 文を D1 側で流すだけで、Worker の中で行を回さない。献立・印・報告のぶつかりの確認も SQL で絞る（同じ日付・枠だけを読む）。

`resolveGroupId` は変えない（所属が1つだけになるので、参加後は招待したグループが返る）。

## 6. 画面

- 設定: 「いっしょに使う人」を実装（メンバー一覧・招待中・招待フォーム・取り消し）
- レシピ一覧の上: 招待が届いているときだけ帯を出し、参加の画面へ
- 参加の画面（/invites/:id）: 2回押しで参加 → 完了表示（移した数・残さなかった献立の枠）→ レシピ一覧へ
- 参加後はクライアントの取得結果（TanStack Query）をすべて捨てて読み直す

## 7. テスト

API（`test/api/group.test.ts` と「グループをまたいだ漏れがないこと」への追加）
- 招待されていない人は参加できない（404）。他人宛ての招待 id でも 404
- 参加前: B から A のレシピ・献立・買い物・報告・メンバー一覧が見えない。A から B のものも見えない
- 参加後: B から A のレシピが見えて編集でき、A から B が持ってきたレシピ・版・メモ・写真が見える
- 献立がぶつかった枠は A の献立が残り、keptPlans に入る。ぶつからない B の献立は移る
- 上限: 招待とメンバーで5人を超える招待は拒否
- 自分・既にメンバーの人は招待できない。メールアドレスは大文字・小文字を区別しない
- 他のグループの招待を取り消せない（404）
- 自分のグループにメンバーがいる人は参加できない（409）
- C（無関係）からは、参加後も A・B のデータが見えない

E2E（`e2e/invite.spec.ts`）
- A がレシピを作り、B を招待 → B でログインして帯から参加 → B にも A のレシピが出る → B が作ったレシピが A にも出る
